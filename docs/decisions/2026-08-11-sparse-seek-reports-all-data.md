# 2026-08-11 · 稀疏檔案查詢一律回答「整個檔案都是資料」，不揭露尾端的洞

**決策**：稀疏檔案查詢一律回答「整個檔案都是資料」，不揭露尾端的洞

**依據**：
（2026-08-11）。
`DiscordFile.seek` 只服務 asyncssh 的 `ranges@asyncssh.com` 探詢，`SEEK_DATA` 回原位、
`SEEK_HOLE` 回檔案大小，位置到了或超過結尾回 `ENXIO`。
**不選「誠實回答」的理由是失敗方向不對稱**：`_covered_end()` 明明知道洞從哪開始，
照實回答還能省掉傳輸那串零；但用戶端預設 `sparse=True`，而在那個模式下
**「傳得比較少」是預期而不是錯誤**——洞的位置早報一個位元組，結果就是下載回來的檔案
大小正確、內容是零，兩端都不會有任何一行 log。宣稱全是資料則不可能這樣壞，
而且那正是 2.21 之前的協定行為，所以沒有任何傳輸改變形狀。
**省下來的頻寬只有稀疏尾端那一段**，等到真的量到它在浪費頻寬再回來換，不是現在。
**`seek` 刻意不是通用的**：這個 handle 沒有檔案位置（讀取自帶 offset），
所以其他 `whence` 一律 `NotImplementedError`，而不是回一個呼叫端有資格相信的數字。
代價與提醒：這條規則只有 Linux 會執行到，**Windows 上測不出任何差別**，
所以 `tests/test_sparse_ranges.py` 直接對 `seek` 斷言，不繞路走真的用戶端。
