# 產出專案藍圖 BLUEPRINT.md

掃過整份專案，產出一份能讓我在短時間內重新掌握全局重點的藍圖文字說明，
並明確指出當前架構的具體優缺點。

## 讀者設定

讀者是「隔了一段時間回來的專案作者」，也可能拿去對外介紹。因此：

- 預設我已忘記細節，但看得懂程式、不需要基礎名詞教學。
- 重點在**為什麼這樣設計**、**目前走到哪**、**哪裡有問題**，而不是逐檔逐函式導覽。
- 語言用繁體中文；程式碼識別字、套件名、指令保留原文。
- 全文控制在能一次讀完的長度（目標 400～700 行）。寧可精簡到位，不要流水帳。

## 執行方式

- **主 agent 直接全掃，不要委派 subagent。**（專案規模不大，拼接落差的成本高於好處。）
- 掃描範圍：`src/`、`tests/`、`Dockerfile`、`docker-compose.yml`、`requirements*.txt`、
  `pytest.ini`、`.env.example`、`.gitignore`、`.vscode/`、`.claude/`，
  以及既有文件 `README.md`、`CLAUDE.md`、`SOP.md`、`ROADMAP.md`、`missing_info.md`、
  `design-multi-user.md`、`design-node-identity-integrity.md`、`session-handoff.md`。
- 跳過：`venv/`、`.pytest_cache/`、`.git/` 內容物。
- 讀 `git log` 近 20～30 筆掌握演進脈絡；不要只靠文件，**文件可能落後於程式碼**。
- **以程式碼為準**。文件與實作衝突時，寫下實際行為，並把衝突本身列成一個缺點項。
- 不要為了填滿章節而編造。查不到的就寫「未確認」，並說明要看哪裡才能確認。

## 輸出

寫到專案根目錄 `BLUEPRINT.md`。

**寫入前**：若 `BLUEPRINT.md` 已存在，先複製成 `BLUEPRINT.md.bak`（直接覆蓋既有 .bak，不必問）。
若不存在就直接建立。

**寫入邊界（硬性）**：這個指令只能寫 `BLUEPRINT.md` 和 `BLUEPRINT.md.bak`，
其他所有檔案一律唯讀。掃到值得記進 `ROADMAP.md` / `missing_info.md` 的事，
**不要自己寫進去**，在對話裡列出來讓我決定。

## 藍圖結構

依序包含以下章節：

### 1. 一頁摘要
這個專案是什麼、解決什麼問題、目前完成度（能跑什麼／還不能跑什麼）。5～10 行內講完。

### 2. 工具鏈與環境
- 語言、執行環境版本、關鍵相依套件（含用途，不要只貼清單）
- Docker / docker-compose 的服務組成與各自職責
- 測試工具與設定（pytest 設定、測試怎麼跑）
- `.env` 需要的每個變數：名稱、用途、必填與否、從哪裡取得
- 依賴的外部服務與其限制（例如 Discord API 的檔案大小 / rate limit）

### 3. 程式架構與資料流
- `src/` 模組拆解表：模組 → 職責 → 對外介面 → 被誰呼叫
- 完整資料流敘述（上傳路徑、下載路徑），從入口一路走到落地
- 檔案分塊、索引／中繼資料的儲存位置與格式
- 狀態存在哪裡、跨執行如何延續

### 4. 安全與加密設計
- KDF（Argon2id）參數與選擇理由
- 金鑰的產生、保存、輪替與使用範圍
- 加密與完整性驗證的實際涵蓋範圍——**明確寫出哪些部分「沒有」被保護**
- `missing_info.md` 已記錄的缺口，逐條標注：已修復 / 仍存在 / 已改變形態

### 5. 工作流程
- 從零把環境跑起來的步驟（可直接照做）
- 日常開發循環：改碼 → 測試 → 驗證
- 部署 / 重啟流程
- `CLAUDE.md` 定下的協作規則摘要：決策分級、提問機制、委派邊界、累積型檔案觸發規則
- `SOP.md` 現有條目的一行式索引

### 6. 圖表
2～3 張 mermaid 圖，只畫最關鍵的。建議選：上傳／下載資料流、模組依賴、金鑰生命週期。
超過 3 張就是畫太多。

### 7. 架構優缺點評估
本節是重點，不要草率帶過。

**優點**：逐條寫，每條說明「好在哪裡、在什麼情境下會兌現這個好處」。

**缺點**：每條包含四個欄位，用清單或表格呈現：
- **問題**：具體是什麼，附上檔案路徑與行號
- **後果**：什麼情境下會出事、出什麼事
- **建議**：怎麼改，改動範圍多大
- **嚴重度**：`高` / `中` / `低`

嚴重度判準：
- `高` — 會造成資料遺失、資料損毀無法察覺、金鑰或明文外洩、或阻擋正式上線
- `中` — 功能上可運作但有明確的正確性或維護性風險，累積下去會變貴
- `低` — 體驗、整潔度、未來擴充性；不修也不會壞

缺點依嚴重度由高到低排序。**不要為了湊數把低嚴重度的事寫成高。**
如果某一級一項都沒有，就寫「無」。

### 8. 已知未決事項
`ROADMAP.md` / `missing_info.md` / 兩份 `design-*.md` 裡尚未收斂的決策點，
以及這次掃描新發現、但屬於「需要我拍板」的問題。
